# v0.1.0-alpha.1 - monitoring preview

Prepared notes for a draft prerelease. Publication is a separate step. This is
early software for evaluation, not a production-readiness certification or a
guaranteed Cloudflare spending ceiling.

## Included

- Observe-by-default Workers usage signals, subscription inventory and available
  rated-charge evidence; unavailable or stale evidence stays unknown.
- Configurable budget warnings and native email, Telegram, Slack and Discord
  delivery, with recipient binding and independent retry state.
- Optional read-only sampler and independent watcher for guard liveness, delayed
  notifications, positive subscription fees, Worker/zone drift and lost coverage.
- Explicitly armed actions for approved stateless HTTP Workers only: non-forced
  deletion or workers.dev/preview endpoint disablement. No other product actions.

Python 3.11+ and the standard library suffice. Live service installation requires
Linux/systemd. There is no hosted dashboard or automatic monitoring installation.

## Try the synthetic demo

From the reviewed source checkout, without credentials or provider access:

```sh
python3 -B -m examples.monitoring_demo
```

Use `python` on Windows. The demo uses the real monitoring logic, fixed synthetic
observations, temporary SQLite state and an in-memory receiver. It demonstrates
deduplication, missing evidence that cannot recover an incident, and affirmative
recovery. Temporary files are removed; no messages or provider writes are sent.
It does not demonstrate live collection or cutoff. Run the full source tests with
`python3 -B -m unittest discover -s tests -v` and `git diff --check`.

## Before any installation or upgrade

Use the exact reviewed source commit recorded in the draft release, not a moving
branch. Follow [getting started](../getting-started.md), [operations](../runbook.md)
and [independent monitoring](../monitoring.md). Old example source pins and dated
verification records do not establish compatibility with an existing installation.

The sampler requires guard database schema 6. Inspect the installed version and
schema read-only first. Before an approved upgrade, stop the managed timer, wait
for in-flight work and make a protected, verified backup of configuration, state,
the prior source pin and installation metadata. Use the documented managed update
path; do not edit hash-owned installed files. Initial installs stay observe-only.
Optional monitoring templates are not installed or activated by the main installer.

For rollback, stop only the affected timers and retain incident/action history.
Code and database schema must be compatible: do not point older code at a newer
database or overwrite newer state blindly. Review whether restoring a backup could
lose usage, notification or unresolved-action evidence before any restore. Monitoring
rollback preserves its state and does not uninstall the shared guard or change
provider resources. These notes do not authorize live updates or restoration.

## Verification limits

The new demo and source tests use synthetic evidence and injected delivery.
During preparation on 28 October 2026, Windows/Python 3.14.7 ran 351 tests:
348 passed and three platform skips, with no failures. The demo also completed
under `python -B -O -m examples.monitoring_demo`; its transition checks do not rely
on Python assertions. Its integration test blocks sockets, subprocesses and real
SMTP constructors and inspects the actual SQLite incident state and cleanup.
No installed runtime, provider adapter, installer or service unit changed for this
sharing candidate. Record final commit-specific CI in the GitHub draft release.

Historical [Linux lifecycle](../solution-audit-2026-10-28.md) and
[monitoring verification](../monitoring-verification.md) records retain their dated
scope; they are not new live proof for this candidate.

Provider permissions and completeness, actual reporting latency, adapted systemd
services, SSH provisioning, human notification receipt and a live disposable Worker
cutoff canary require separate verification. Endpoint disablement does not stop
routes or internal invocations. Polling, concurrent changes and failed/uncertain
actions leave exposure. CPU planning reserves are not measured CPU or upper bounds.

Subscription fees, taxes, Registrar renewals and unsupported products are not capped.
Worker/zone inventory is not complete charge-source discovery. Account costs are
not per-domain attribution. See [capabilities](../capabilities.md) and
[automatic cutoff](../automatic-cutoff.md) before evaluating actions.
